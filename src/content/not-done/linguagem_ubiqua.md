Comunicação Eficaz - Linguagem Ubíqua

- Todo software é construído para resolver "problemas"
- No contexto de desenvolvimento de software, a palavra problema não significa necessariamente um problema que possa ser resolvido e finalizado, como um problema matemático. Ele tem um significado muito mais amplo.
- O problema é aquilo que o software resolve. Não necessariamente algo que possa ser finalizado, mas algo que será sempre um problema. Como por exemplo gestão de conhecimento, gestão financeira e etc.
- Um ponto importante sobre a descoberta de conhecimento no desenvolvimento de um software é que a especialidade do domínio deve ficar a cargo dos especialistas de domínio, ao passo que os desenvolvedores não podem nem devem se tornar especialistas de domínio. Entretanto, eles precisam compreender as regras de negócio perfeitamente. E para isso é necessário que eles mantenham uma comunicação eficiente com os especialistas de domínio. Caso contrário, o software desenvolvido pode ter partes onde os requisitos não cobriram perfeitamente ou não tinham alguma especificidade do domínio de negócio que o desenvolvedor deixou passar e no futuro pode impactar o desenvolvimento de novas funcionalidades necessárias para o domínio.
- "Para ser eficiente o software precisa imitar a forma como os especialistas de domínio pensam sobre o problema. Sem entender o problema de negócio e o raciocínio por trás dos requisitos, nossas soluções se limitarão a traduzir as exigências do negócio no código fonte. Mas e se os requisitos não incluírem um caso crucial? Ou não conseguirem descrever um conceito de negócio, limitando a capacidade de implementar um modelo que dê suporte a exigências futuras? Como diz Alberto Brandolini: desenvolvimento de software é um processo de aprendizado, trabalhar com código é um efeito colateral." - Citação ao livro, Capitulo 2 pagina 22
- O maior problema no modelo de desenvolvimento de software tradicional é a falta de uma comunicação eficaz. Em muitos projetos de software que fracassam, o conhecimento dos especialistas de domínio, ou conhecimento de domínio, ele é traduzido a modelos de análise para ser passados para os desenvolvedores e essa tradução é feita geralmente por um analista de sistemas ou algum mediador. E essa tradução busca simplificar o conhecimento de domínio transformando ele nos requisitos daquilo que o software precisa fazer, mas acaba se perdendo a informação crucial sobre o domínio e qual problema ele resolve. E isso acaba distorcendo as informações, fazendo com que esse processo de comunicação seja ineficiente, mais ou menos como um telefone sem fio, onde a mensagem, que seria o conhecimento de domínio, ele muitas vezes fica distorcido, e essa informação distorcida faz com que os engenheiros de software implementem a solução errada ou a solução certa para os problemas errados. E em ambos os casos o resultado é o mesmo, que é um projeto fracassado. Por isso o Domain Driven Design propõe uma forma melhor de passar esse conhecimento dos especialistas de domínio para os engenheiros de software, que é a linguagem ubíqua.
- A linguagem ubíqua serve para que durante o ciclo de desenvolvimento de software não sejam feitas traduções, mas que todos os envolvidos falem a mesma língua. É uma noção básica e bem comum de que todos falarem a mesma língua é muito mais eficiente do que você ficar utilizando traduções. É importante enfatizar que a linguagem ubíqua deve conter apenas termos correlatos ao domínio do negócio. Ela não deve conter jargões técnicos ou qualquer tipo de linguagem que seja de caráter técnico de designers ou de engenheiros de software. Ela deve ser uma linguagem que reflete o domínio de negócio, o problema que ele resolve e de que forma ele resolve, sem entrar em conceitos técnicos, para que tanto especialistas de domínio quanto engenheiros de software, design de UI ou stakeholders consigam compreender.
- Para manter a consistência da linguagem ubíqua, é importante que evitemos termos ambíguos ou sinônimos. Cada termo dentro da linguagem ubíqua deve ter um e apenas um significado dentro do domínio do negócio, para que quando a gente for modelar esse domínio, a gente não tenha confusões ou seja fácil compreender o domínio do negócio. Termos como usuário, visitante, conta são ambíguos e, em muitos casos, sinônimos, mesmo representando coisas diferentes dentro do sistema. Então é importante que a gente evite usar dois ou mais termos que tenham significado ambíguo ou que sejam sinônimos, que podem causar confusão nos diferentes interessados no projeto.
- Uma perspectiva diferente da linguagem UML é a modelagem. Mas para entender modelagem a gente precisa entender o que é um modelo. O modelo não é uma cópia do mundo real, mas ele é algo que o ser humano cria para nos ajudar a entender coisas do mundo real. Um exemplo geral de modelo é um mapa. Qualquer mapa é um modelo, incluindo mapa de navegação, mapa de relevo, mapa-múndi, mapa de metrô e outros. Nenhum mapa representa todos os detalhes do planeta, mas cada mapa contém toda a informação suficiente para que o seu propósito particular seja solucionado.
- Um modelo eficaz é aquele que omite toda a informação desnecessária e contém apenas a informação necessária para que ele resolva o problema que ele foi criado para ser resolvido. Ele é uma abstração e deve conter apenas aquilo que é necessário para abstrair o conceito e resolver o problema que ele tem que resolver.
- A linguagem ubíqua não precisa necessariamente refletir todos os conceitos de domínio do software, porque nesse caso todo mundo que conhece a linguagem ubíqua seriam especialistas de domínio. O que ela precisa fazer é conter tudo aquilo que é suficiente para possibilitar a implementação do sistema para que ele consiga resolver o problema que ele deve solucionar.
- Apesar da linguagem ubíqua ter a sua criação diretamente relacionada à comunicação com os especialistas de negócio, é função de todos aqueles que participam do projeto estar constantemente atualizando a linguagem. O seu uso no dia a dia é fundamental para que, conforme os interessados usem a linguagem ubíqua, novos conceitos do domínio são revelados com o tempo. E é importante utilizar ferramentas como glossários ou casos de uso e testes escritos com Gherkin para que a gente armazene e atualize continuamente a linguagem ubíqua. E isso, além de ajudar a estruturação da linguagem, também facilita a integração de novas pessoas ao projeto.
